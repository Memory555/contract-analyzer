# 合同智能分析平台 v3 技术方案文档

版本：v3.1.0
日期：2026-06-24
状态：已实现（PostgreSQL + 用户隔离）
部署方向：CloudBase 云托管 + PostgreSQL 数据库

## 1. 技术目标

v3 的技术目标是在不重构合同分析主流程的前提下，新增"反馈管理"能力：用户从左侧导航进入反馈管理，选择某条历史合同分析记录，对该记录提交"有帮助"或"有问题"的反馈。系统自动带入分析上下文，**通过 PostgreSQL 云数据库持久化存储**，并实现**用户数据隔离**（不同用户的反馈互不可见）。同时提供"我的云端总览"功能，让用户查看自己提交过的所有云端反馈。

## 2. 改动边界

### 2.1 尽量不动的部分

- 合同分析页主体布局。
- 上传、批量分析、结果展示、导出中心逻辑。
- 现有本地历史记录结构的主要字段。
- 现有模型分析 API `/api/analyze`。

### 2.2 主要新增部分

- 左侧导航新增"反馈管理"。
- 新增 **双标签页** 反馈管理页面组件：
  - Tab 1：提交反馈（基于本地 Dexie 历史）
  - Tab 2：我的云端总览（基于 PostgreSQL 云数据）
- 新增 PostgreSQL 连接池模块 `lib/postgres.ts`。
- 新增用户标识模块 `lib/user-id.ts`（UUID + authedFetch）。
- 新增 `/api/feedback`：POST 提交 + GET 列表/统计，写入/读取 PostgreSQL。
- 新增 `/api/feedback/[id]`：GET 单条详情，双重过滤（ID + user_id）。
- 新增 `CloudFeedbackDashboard` 云端反馈总览组件。
- Dexie 本地库新增 `feedbacks` 表，用于**离线状态追踪**（pending/submitted/failed），非权威数据源。
- 保留 CloudBase 文档数据库适配层 `lib/cloudbase.ts` 作为备用（当前未启用）。

## 3. 前端架构

页面枚举扩展为 `analysis | exports | feedback | settings`。导航项新增 `反馈管理`，页面渲染分支新增 `FeedbackManagementPage`。合同分析页主体 JSX 不做结构性改动。

### 3.1 反馈管理页面布局

FeedbackManagementPage 采用 **Tab 切换设计**：

- **Tab 1 — 提交反馈**：左侧历史合同分析列表（Dexie 本地），右侧选中记录摘要和反馈操作流程。
- **Tab 2 — 我的云端总览**：统计卡片 + 分类分布 + 筛选栏 + 分页列表 + 展开详情（PostgreSQL 云端读取）

### 3.2 提交反馈流程（Tab 1）

`选择历史记录 -> 有帮助/有问题 -> 问题原因 -> 可选说明 -> 提交`

其中"有帮助"直接提交，"有问题"才进入原因选择。提交时使用 `authedFetch` 自动注入 `x-user-id` 头。

### 3.3 用户标识机制（lib/user-id.ts）

```ts
// getUserId(): 生成 UUID 存入 localStorage（key: "fb_user_id"）
// authedFetch(): 包装原生 fetch，自动附加 x-user-id 请求头
```

## 4. 数据模型

### 4.1 反馈类型定义

```ts
export type FeedbackType = "helpful" | "problem";
export type FeedbackProblemCategory =
  | "missing_clause"
  | "wrong_judgment"
  | "wrong_risk_level"
  | "unclear"
  | "other";

// 本地 Dexie 缓存记录（离线状态追踪）
export interface AnalysisFeedbackRecord {
  id: string;
  contractId: string;
  batchId: string;
  fileName: string;
  feedbackType: FeedbackType;
  problemCategory?: FeedbackProblemCategory;
  comment?: string;
  analysisTime: string;
  modelName: string;
  promptVersion: string;
  resultSummary: string;
  riskItemCount: number;
  contractText: string;
  status: "pending" | "submitted" | "failed";
  createdAt: string;
  updatedAt: string;
}

// 云端反馈列表项
export interface CloudFeedbackListItem {
  id: number;           // PostgreSQL SERIAL 主键
  contractId: string;
  fileName: string;
  feedbackType: FeedbackType;
  problemCategory?: FeedbackProblemCategory;
  comment?: string;
  modelName: string;
  riskItemCount: number;
  createdAt: string;
}

// 云端反馈统计
export interface CloudFeedbackStats {
  totalCount: number;
  helpfulCount: number;
  problemCount: number;
  byCategory: Record<string, number>;
}
```

### 4.2 PostgreSQL 表结构

表名：`analysis_feedback`

| 列名 | 类型 | 说明 |
|------|------|------|
| id | SERIAL PK | 自增主键 |
| user_id | VARCHAR(64) NOT NULL | 用户唯一标识（浏览器 UUID） |
| contract_id | TEXT NOT NULL | 合同 ID |
| batch_id | TEXT | 批次 ID |
| file_name | TEXT | 原始文件名 |
| feedback_type | VARCHAR(16) NOT NULL | helpful / problem |
| problem_category | VARCHAR(32) | 问题分类（仅 problem 时有值） |
| comment | TEXT | 用户补充说明 |
| analysis_time | TIMESTAMPTZ | 分析时间 |
| model_name | VARCHAR(128) | 模型名称 |
| prompt_version | VARCHAR(64) | Prompt 版本 |
| result_summary | TEXT | 分析结果摘要 |
| risk_item_count | INTEGER DEFAULT 0 | 风险项数量 |
| contract_text | TEXT | 合同原文（mammoth 提取的纯文本） |
| status | VARCHAR(16) DEFAULT 'submitted' | 状态 |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

索引：`idx_feedback_user_id`、`idx_feedback_created_at`、`idx_feedback_type`、`idx_feedback_contract_id`、`idx_feedback_problem_cat`

### 4.3 本地 Dexie 缓存（非权威）

Dexie `feedbacks` 表字段：`id, contractId, batchId, feedbackType, problemCategory, status, createdAt, updatedAt`

用途：追踪本地提交状态（是否已成功发送到云端），不作为数据查询来源。

## 5. 后端 API

### 5.1 POST /api/feedback — 提交反馈

职责：

1. 从请求头 `x-user-id` 获取用户标识（无则返回 503）。
2. 校验 feedbackType、problemCategory（如有）、comment 长度、必要上下文字段。
3. 写入 PostgreSQL `analysis_feedback` 表（含 user_id）。
4. 同步写入本地 Dexie 记录状态为 submitted。

请求结构：

```ts
{
  contractId: string;
  batchId: string;
  fileName: string;
  feedbackType: "helpful" | "problem";
  problemCategory?: FeedbackProblemCategory;
  comment?: string;
  analysisTime: string;
  modelName: string;
  promptVersion: string;
  resultSummary: string;
  riskItemCount: number;
  contractText: string;
}
```

响应结构：`{ feedbackId: number; stored: boolean; message: string }`

### 5.2 GET /api/feedback — 分页列表 + 统计

职责：

1. 从请求头 `x-user-id` 获取用户标识（无则返回 503）。
2. 支持分页参数 `page`（默认 1）、`pageSize`（默认 20）。
3. 单次 SQL 查询完成分页列表 + 全局统计（`COUNT FILTER (WHERE ...)`）。
4. SQL 列别名使用 camelCase（如 `AS "contractId"`），与 TS 类型一致。
5. 所有结果按 `user_id` 过滤。

响应结构：

```ts
{
  list: CloudFeedbackListItem[];
  total: number;
  page: number;
  pageSize: number;
  stats: CloudFeedbackStats;
}
```

### 5.3 GET /api/feedback/[id] — 单条详情

职责：

1. 从请求头 `x-user-id` 获取用户标识。
2. 查询条件：`WHERE id = $1 AND user_id = $2`（双重过滤）。
3. 返回完整记录（含 contractText）。
4. ID 不存在或不属于当前用户 → 返回 404（统一处理，不泄露信息差异）。

## 6. PostgreSQL 连接池设计（lib/postgres.ts）

```ts
import { Pool } from "pg";

const pool = new Pool({
  host: process.env.PG_HOST,
  port: Number(process.env.PG_PORT) || 5432,
  user: process.env.PG_USER,
  password: process.env.PG_PASSWORD,
  database: process.env.PG_DATABASE || "postgres",
  options: "-c client_encoding=UTF8",    // 防止中文乱码
  max: 10,                                 // 最大连接数
  idleTimeoutMillis: 30000,
  connectionTimeoutMillis: 5000,
});

// ensureTable() — 首次调用时自动建表 + ALTER ADD COLUMN user_id + 创建索引
// getPool() — 返回连接池实例供 API 使用
```

关键设计决策：

- **UTF8 编码**：连接池配置 `options: "-c client_encoding=UTF8"`，防止 Windows 环境下中文乱码。
- **自动建表**：`CREATE TABLE IF NOT EXISTS`，首次部署无需手动执行 DDL。
- **兼容旧表**：`ALTER TABLE ADD COLUMN IF NOT EXISTS user_id`，支持从无 user_id 的旧表平滑迁移。
- **列别名映射**：SQL 中所有返回列使用 `AS "camelCaseName"` 格式，避免前端 snake_case → camelCase 手动转换。

## 7. CloudBase 适配策略（历史方案，已弃用）

> ⚠️ 以下内容为原始方案，因 CloudBase 文档数据库配额限制已弃用。保留作为参考和备用。

原计划将 Next.js standalone 容器部署到 CloudBase，反馈 API 随 Next.js 服务一起部署。后续接入 CloudBase 文档型数据库时建议：集合名称 `analysis_feedback`；权限为服务端写入、管理端读取；通过 `CLOUDBASE_ENV_ID` 和服务端凭据或 CloudBase 运行时默认凭据连接。

**实际采用方案**：CloudBase 云托管 + CloudBase PostgreSQL（详见第 6 节）。

## 8. 自动上下文生成

- `analysisTime`：历史分析记录 `updatedAt` 或 `createdAt`。
- `modelName`：优先使用设置中的模型名，其次使用环境默认占位。
- `promptVersion`：固定为 `v3-feedback-001`。
- `resultSummary`：由付款计划数量、质保字段数量、风险项数量和置信度生成摘要。
- `riskItemCount`：`result.issues.length`。
- `contractText`：合同分析成功后保存到历史合同记录中（mammoth.js 提取 .docx 纯文本），反馈时自动带入。
- `user_id`：由 `getUserId()` 从 localStorage 读取或生成 UUID。

1. 编译通过。

4. 点击"反馈管理"后显示双标签页（提交反馈 / 我的云端总览）。

   c. 点击"有问题"后才显示问题原因选择。
   d. 可选填写说明并提交。

## 10. 技术风险与后续

### 已解决的风险

| 风险 | 解决方案 | 状态 |
|------|----------|------|
| CloudBase 文档数据库写入配额限制 | 迁移到 PostgreSQL | ✅ 已解决 |
| 不同用户看到彼此的反馈 | user_id 字段隔离 | ✅ 已解决 |
| Windows 环境 curl 中文乱码 | pg 连接池 UTF8 配置 | ✅ 已解决 |
| Dev server 被 HTTP_PROXY 卡住 | 启动时清空代理变量 | ✅ 已解决 |
| PostgreSQL snake_case 与前端 camelCase 不匹配 | SQL 列别名 AS "camelCase" | ✅ 已解决 |

### 后续优化方向

- 历史合同原文属于敏感数据，商用前需增加授权提示或脱敏策略。
- 当前用户标识基于浏览器 UUID（localStorage），清理缓存后会生成新 ID 导致历史数据不可见。后续可考虑接入登录系统。
- 若未来要跨设备查看反馈管理，需要把历史分析记录也迁移到云端。
- 可考虑增加反馈数据的导出功能（CSV/Excel）。
- 可考虑增加管理员后台查看所有用户反馈汇总的能力。
