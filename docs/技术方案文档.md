# 合同智能分析平台技术方案文档

版本：V1.0  
日期：2026-06-17  
适用范围：前后端开发、OpenAI LLM 接入、Excel 导出、Vercel / 阿里云部署选型

## 1. 技术目标

平台需要完成以下闭环：

上传合同文件 → 文档解析为文本 → 调用 OpenAI LLM 输出结构化 JSON → 后端校验与归一化 → 前端展示结果 → 生成并下载 Excel。

V1.0 优先保证单合同分析稳定可用，后续再扩展批量任务、历史记录、字段配置和审查工作流。

## 2. 总体架构

建议采用前后端分离架构。

```text
浏览器前端
  ↓
上传合同 / 查询结果 / 下载 Excel
  ↓
后端 API
  ↓
文档解析服务
  ↓
OpenAI LLM 结构化提取
  ↓
结果校验与 Excel 生成
```

### 2.1 推荐技术栈

| 层级 | 推荐方案 | 说明 |
|------|----------|------|
| 前端 | React + Vite 或 Next.js | 适合做后台工作台和后续功能扩展 |
| UI | Ant Design / Arco Design / 自定义 CSS | 合同表格和后台系统建议优先选成熟组件库 |
| 后端 | Python FastAPI | 文档解析、LLM 调用、Excel 生成生态更顺 |
| 文档解析 | pdfplumber / PyMuPDF / python-docx / LibreOffice headless | PDF、DOCX、DOC 兼容处理 |
| LLM | OpenAI Responses API | 用于合同信息抽取和问题识别 |
| 结构化输出 | OpenAI Structured Outputs + JSON Schema | 降低 LLM 返回格式不稳定风险 |
| Excel | openpyxl | 生成多 Sheet xlsx |
| 部署 | 前端 Vercel；后端优先阿里云 | 文档解析和 LibreOffice 更适合后端容器或云服务器 |

## 3. 前端方案

### 3.1 页面结构

前端采用左侧导航工作台：

- 工作台
- 合同分析
- 问题审查
- 导出中心
- 设置

当前优先实现“合同分析”页面。

### 3.2 核心状态

前端需要实现以下状态：

| 状态 | 说明 |
|------|------|
| 初始态 | 上传区域可点击或拖拽 |
| 校验失败 | 格式错误、大小超限 |
| 上传中 | 展示文件名和进度条 |
| 解析中 | 展示加载态和预计耗时 |
| 解析成功 | 展示问题、付款计划、质保明细、置信度、下载配置 |
| 解析失败 | 展示失败原因和重新上传入口 |

### 3.3 前端数据展示规则

- 合同问题放在结果顶部。
- 问题严重程度支持：错误、警告、提示。
- 付款描述多条时直接换行展示。
- 质保明细支持固定核心字段和动态扩展字段。
- 表格行保留“涉及位置”和“查看原文位置”入口。
- 下载前允许勾选是否包含“合同问题”Sheet。

## 4. 后端 API 方案

### 4.1 API 划分

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/contracts/analyze` | POST | 上传合同并返回分析结果 |
| `/api/contracts/export` | POST | 按当前结果和下载选项生成 Excel |
| `/api/health` | GET | 健康检查 |

V1.0 可先不做任务队列，上传后同步解析并返回结果。若真实解析超过 30 秒，应升级为异步任务：

- `/api/contracts/jobs` 创建任务
- `/api/contracts/jobs/{job_id}` 查询状态
- `/api/contracts/jobs/{job_id}/export` 下载结果

### 4.2 后端模块

建议目录：

```text
backend/
├── main.py
├── config.py
├── parser.py
├── llm_client.py
├── schemas.py
├── excel_writer.py
├── storage.py
└── requirements.txt
```

| 模块 | 职责 |
|------|------|
| `main.py` | FastAPI 路由入口 |
| `config.py` | 环境变量和部署配置 |
| `parser.py` | PDF / DOC / DOCX 转文本 |
| `llm_client.py` | OpenAI 调用封装 |
| `schemas.py` | Pydantic 请求、响应和 LLM 输出结构 |
| `excel_writer.py` | Excel 生成 |
| `storage.py` | 临时文件保存与清理 |

## 5. 文档解析方案

### 5.1 文件格式处理

| 文件类型 | 处理方式 |
|----------|----------|
| PDF | 优先提取文本层；如文本为空或极少，提示扫描件暂不支持 |
| DOCX | 使用 python-docx 提取段落和表格 |
| DOC | 使用 LibreOffice headless 转为 DOCX 后再解析 |

### 5.2 解析结果要求

文档解析阶段应输出：

- 合同纯文本
- 段落序号或近似位置
- 表格文本
- 原文片段索引

这些信息用于后续“涉及位置”和“查看原文位置”。

## 6. OpenAI LLM 接入方案

### 6.1 API 选择

建议使用 OpenAI Responses API。OpenAI 官方文档建议文本生成类应用优先使用 Responses API；如果使用 reasoning model，Responses API 尤其适合。

结构化抽取建议使用 Structured Outputs，并通过 JSON Schema 约束模型输出。OpenAI 文档说明 Structured Outputs 可让模型输出符合开发者提供的 JSON Schema，且比普通 JSON mode 更能保证 schema adherence。

### 6.2 Base URL 配置

OpenAI 调用层需要支持 `base_url` 配置，不能把官方 OpenAI endpoint 写死。

原因：

- 部署到阿里云后，可能需要通过企业网络出口、代理网关或 API 中转服务访问 OpenAI。
- 后续可能接入兼容 OpenAI API 协议的模型服务。
- 本地开发、测试环境、生产环境可能使用不同访问地址。

建议环境变量：

```text
OPENAI_API_KEY=...
OPENAI_BASE_URL=https://api.openai.com/v1
OPENAI_MODEL=...
```

调用封装要求：

- `OPENAI_BASE_URL` 为空时使用 SDK 默认地址。
- `OPENAI_BASE_URL` 有值时传入 OpenAI SDK client。
- 所有 OpenAI 调用只能经过 `llm_client.py`，业务代码不要直接实例化 SDK。
- 日志中不得输出完整 API Key。

Python SDK 示例：

```python
from openai import OpenAI

client = OpenAI(
    api_key=settings.openai_api_key,
    base_url=settings.openai_base_url or None,
)
```

注意：如果使用第三方中转或兼容服务，需要确认其是否完整支持 Responses API 和 Structured Outputs。如果不支持，需要在技术上降级到其兼容的接口，并在代码中隔离适配层。

### 6.3 模型建议

当前暂定使用 OpenAI。模型建议分两档配置：

| 配置项 | 建议 |
|--------|------|
| 默认高质量模型 | 使用当前 OpenAI 推荐的较新 GPT 模型，生产环境固定具体快照 |
| 成本优先模型 | 预留轻量模型配置，用于测试或低风险合同 |

生产环境不要只写“latest”或浮动别名，建议通过环境变量固定模型名，例如：

```text
OPENAI_MODEL=gpt-5.5-2026-04-23
```

具体模型名在正式开发前再按 OpenAI 控制台可用模型确认。

### 6.4 LLM 输出结构

后端应要求 LLM 返回统一 JSON：

```json
{
  "issues": [],
  "payment_plan": [],
  "warranty": {
    "core_fields": [],
    "extra_fields": []
  },
  "confidence": {
    "overall": 0.86,
    "payment_plan": 0.9,
    "warranty": 0.82,
    "issues": 0.78
  }
}
```

关键规则：

- 所有问题必须包含类型、严重程度、描述、涉及位置、原文片段。
- 严重程度枚举为 `error`、`warning`、`info`。
- 付款计划必须保留多条付款描述数组，前端负责换行显示。
- 质保字段分为核心字段和扩展字段。
- 置信度由 LLM 给出初始值，后端可结合字段完整性做二次校正。

### 6.5 稳定性策略

- 使用 JSON Schema 约束输出。
- 使用 Pydantic 做二次校验。
- LLM 返回不合法时重试一次。
- 仍失败时返回解析失败，并保留可诊断错误。
- 对合同金额、付款比例合计、质保期冲突等可用规则校验补强，不完全依赖 LLM。
- 对 `base_url` 访问失败、超时、返回格式不兼容等情况，前端统一提示“解析服务暂不可用，请稍后重试”，后端日志保留具体错误类型。

## 7. Excel 导出方案

Excel 文件名：

```text
合同分析结果_{原文件名}.xlsx
```

默认 Sheet：

| Sheet | 内容 |
|-------|------|
| 付款计划明细 | 阶段、比例、付款描述、支付时限、备注、涉及位置 |
| 质保明细 | 核心字段、扩展字段、内容、涉及位置 |
| 合同问题 | 问题类型、严重程度、问题描述、涉及位置 |

下载前允许用户取消“合同问题”Sheet。

Excel 样式：

- 中文表头
- 表头加粗
- 浅蓝色背景
- 自动列宽
- 多条付款描述在同一单元格内换行

## 8. 部署方案

### 8.1 方案 A：Vercel 前端 + 阿里云后端

这是当前最推荐方案。

| 部分 | 部署位置 | 原因 |
|------|----------|------|
| 前端 | Vercel | 部署简单、预览方便、适合静态和前端应用 |
| 后端 | 阿里云 ECS / SAE / 容器服务 | 文档解析依赖 LibreOffice、Python 包和临时文件，更适合稳定后端环境 |
| 文件临时存储 | 阿里云后端本地临时目录或 OSS | 上传文件仅用于本次分析，定时清理 |
| 密钥 | 阿里云环境变量 | OpenAI API Key 不暴露给前端 |

适用场景：

- 需要快速上线网页。
- 后端有文档转换、Excel 生成等运行时依赖。
- 后续可能扩展任务队列、历史记录或 OSS 存储。

### 8.2 方案 B：前后端都部署在阿里云

适合更偏企业内网或统一云资源管理的场景。

| 部分 | 部署位置 |
|------|----------|
| 前端 | 阿里云 OSS 静态网站 / Nginx |
| 后端 | ECS / SAE / 容器服务 |
| 存储 | OSS |
| 日志 | 阿里云日志服务 SLS |

优点是网络、日志、存储和安全策略统一；缺点是前端预览和迭代便利性略低于 Vercel。

### 8.3 方案 C：全部 Vercel

不作为首选。

原因：

- DOC 转 DOCX 可能依赖 LibreOffice，不适合轻量 Serverless 环境。
- 文件解析和 Excel 生成有临时文件和运行时依赖。
- LLM 调用加文档解析可能超过 Serverless 超时限制。

如果只支持 DOCX / 文本层 PDF，且不处理 DOC，可以作为早期 Demo 方案。

### 8.4 方案 D：无独立云服务器，浏览器本地存储 + Serverless API

可以不使用传统云服务器，但不建议做成“完全纯前端”。

推荐形态是：

```text
浏览器前端
  ↓
IndexedDB 保存本地任务、分析结果、导出记录
  ↓
Vercel / 阿里云函数计算 Serverless API
  ↓
OpenAI / OpenAI-compatible base_url
```

#### 可放在浏览器本地的内容

| 内容 | 是否适合放浏览器 |
|------|------------------|
| 上传文件的临时选择状态 | 适合 |
| 解析后的结构化结果 | 适合 |
| 历史分析记录 | 适合，使用 IndexedDB，但应设置保留期 |
| 用户下载配置 | 适合 |
| Excel 导出偏好 | 适合 |
| OpenAI API Key | 不适合 |
| 后端系统 Prompt | 不适合 |
| 需要保密的合同全文长期存储 | 不建议 |

浏览器本地数据库建议使用 IndexedDB，可通过 Dexie.js 这类封装库降低开发复杂度。

建议默认保留本地分析记录 15 天，并在应用启动时自动清理过期记录，避免合同数据长期占用浏览器空间。

#### 为什么仍需要 Serverless API

即使不使用云服务器，也建议保留一个极轻量后端接口，原因是：

- OpenAI API Key 不能放在前端，否则会暴露给用户浏览器。
- 合同分析 Prompt、JSON Schema、重试策略不应完全暴露在前端。
- OpenAI `base_url`、模型名和调用策略需要服务端统一控制。
- 后续如果接入企业代理网关或兼容 OpenAI 的中转服务，前端不需要改。

#### 限制

无独立云服务器方案需要控制能力边界：

| 能力 | 可行性 |
|------|--------|
| DOCX 解析 | 可行，可前端解析或 Serverless 解析 |
| 文本层 PDF 解析 | 可行，但前端解析质量需要验证 |
| DOC 转 DOCX | 不推荐，通常依赖 LibreOffice，不适合纯前端或轻量 Serverless |
| 大文件解析 | 不推荐，浏览器和 Serverless 都可能受限 |
| 长耗时任务 | 不推荐，Serverless 有超时限制 |
| 批量合同分析 | 不推荐作为 V1.0 无服务器方案 |

#### 适用结论

如果 V1.0 目标是快速上线轻量版，可以采用：

```text
前端：Vercel
本地存储：IndexedDB
轻后端：Vercel Serverless Functions 或阿里云函数计算
LLM：OpenAI / OpenAI-compatible base_url
文件范围：优先 DOCX + 文本层 PDF，暂缓 DOC
```

如果必须稳定支持 DOC、复杂 PDF、大文件和后续批量任务，仍建议使用阿里云后端服务。

## 9. 安全与隐私

- OpenAI API Key 只放在后端环境变量中。
- 前端不直接调用 OpenAI。
- 上传文件默认只做临时处理，不长期保存。
- 临时文件使用任务 ID 隔离，并定时清理。
- 日志中不记录完整合同正文，只记录任务 ID、文件名、耗时和错误类型。
- 对外部署时限制上传文件大小和文件类型。

## 12. 当前建议结论

建议优先采用：

```text
前端：React + Vite / Next.js，部署到 Vercel
后端：FastAPI，部署到阿里云 ECS / SAE / 容器服务
LLM：OpenAI Responses API + Structured Outputs
文档解析：Python 解析库 + LibreOffice headless
Excel：openpyxl
```

这套方案能兼顾快速原型、后续扩展和生产部署稳定性。

如果希望降低运维成本，也可以先采用：

```text
前端：React + Vite / Next.js，部署到 Vercel
本地数据：IndexedDB
轻后端：Vercel Serverless Functions / 阿里云函数计算
LLM：OpenAI Responses API 或兼容接口，支持 OPENAI_BASE_URL
文件范围：优先 DOCX + 文本层 PDF，暂不承诺 DOC 转换
```

该方案更轻，但文件兼容性和长任务稳定性弱于阿里云后端。
