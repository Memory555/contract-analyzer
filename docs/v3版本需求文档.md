# 合同智能分析平台 v3 版本需求文档

版本：v3.1.0
日期：2026-06-24
状态：已实现（PostgreSQL + 用户隔离）
基线版本：v2.0.0
部署方向：CloudBase 云托管 + PostgreSQL 数据库

## 1. 版本定位

v3 在现有合同分析能力基础上，正式引入后端能力和效果反馈闭环。反馈模块不改变现有合同分析页面的主体设计，而是在左侧导航增加"反馈管理"，让用户对历史合同分析记录进行反馈。

当前合同分析能力主要围绕示例合同模板设计，现实合同中可能存在格式混乱、条款缺失、补充协议、多版本合同、非常规付款条件、质保表述不完整等情况。v3 的目标不是立即解决所有异常合同，而是先稳定采集用户对历史分析结果的反馈，把真实问题沉淀为后续 prompt 调整、模型策略优化和回归测试样本。

核心闭环：

上传合同 -> 系统分析 -> 形成历史分析记录 -> 进入反馈管理 -> 选择某次历史合同分析 -> 提交反馈 -> **PostgreSQL 云端持久化** -> 后续在"我的云端总览"中查看与复盘

## 2. 版本目标

1. 保持现有合同分析页面主体设计不变。
2. 在左侧导航增加"反馈管理"入口。
3. 支持用户在反馈管理中选择某个历史合同分析记录进行反馈。
4. 支持"有帮助"一键提交。
5. 支持"有问题"后再进入问题类型选择和可选补充说明。
6. 后台自动采集分析时间、模型名称、prompt 版本、分析结果摘要、风险项数量、合同原文。
7. 将反馈数据保存到 **CloudBase PostgreSQL** 数据库（替代原 CloudBase 文档数据库方案）。
8. 实现用户数据隔离：不同用户的反馈互不可见。
9. 新增"我的云端总览"功能：查看个人已提交的云端反馈列表和统计信息。

## 4. 技术选型变更记录

> ⚠️ 以下为 v3 开发过程中的技术决策调整

### 4.1 存储层迁移：从 CloudBase 文档数据库到 PostgreSQL

**原因**：CloudBase 免费版文档数据库存在写入配额限制（`LimitExceeded.OutOfWriteRequestQuota`），无法满足生产环境使用。

**方案**：
- 数据库引擎：**PostgreSQL 17.10**（CloudBase 托管实例）
- 驱动：**node-postgres** (`pg` + `@types/pg`)
- 连接池：内置连接池管理，配置 UTF8 编码防止中文乱码
- 自动建表：首次请求时自动创建 `analysis_feedback` 表及索引

### 4.2 用户隔离机制

**原因**：原始方案所有用户共享同一张表，可看到彼此的反馈内容，存在安全隐患。

**方案**：
- 每个浏览器自动生成唯一 UUID，存储在 `localStorage`
- 所有 API 请求通过 `authedFetch` 自动携带 `x-user-id` 请求头
- PostgreSQL 表新增 `user_id VARCHAR(64)` 列
- 所有查询均附带 `WHERE user_id = $N` 条件
- 跨用户访问（无 userId 或 ID 不匹配）返回 404

## 5. 用户反馈原则

v3 反馈设计遵循"合同分析不打扰，反馈流程再进入"的原则。

用户侧路径：

1. 从左侧进入"反馈管理"。
2. 选择某个历史合同分析。
3. 点击"有帮助"，直接完成反馈。
4. 或点击"有问题"，进入问题类型选择。
5. 选择问题类型后，可选填写一句补充说明并提交。
6. （可选）切换到"我的云端总览"标签页，查看已提交的云端反馈统计和历史。

系统不要求用户填写分析时间、模型、prompt、风险数量、合同原文等技术上下文。

## 6. 功能需求

### 6.1 左侧反馈管理入口

| 项目 | 说明 |
|------|------|
| 触发位置 | 左侧导航，与"合同分析""导出中心""设置"同级 |
| 页面原则 | 不改变现有合同分析页面主体布局 |
| 进入后 | 显示 **双标签页**：提交反馈 / 我的云端反馈 |

验收标准：

- 左侧导航出现"反馈管理"。
- 点击"反馈管理"后，显示包含两个标签页的反馈管理界面。
- 原合同分析页面上传、分析、导出布局不因 v3 反馈模块改版。

### 6.2 提交反馈（Tab 1）

| 项目 | 说明 |
|------|------|
| 数据来源 | 本地 Dexie 历史记录 |
| 列表字段 | 合同名称、分析时间、风险项数量、反馈状态 |
| 详情字段 | 分析结果摘要、风险项、付款计划、质保摘要 |
| 反馈状态 | 未反馈、已提交（本地 Dexie 状态追踪） |

验收标准：

- 用户可以从本地历史记录中选择某个合同分析。
- 选择后右侧展示该分析的摘要和反馈操作。
- 已反馈记录能显示本地提交状态。

### 6.3 历史分析一键反馈

| 项目 | 说明 |
|------|------|
| 触发位置 | 反馈管理的"提交反馈"标签页中 |
| 默认状态 | 显示"有帮助""有问题"两个操作 |
| 有帮助 | 点击后直接提交正向反馈至 PostgreSQL |
| 有问题 | 点击后进入问题原因选择，不在第一步展示全部表单 |
| 重复提交 | 同一历史分析默认只保留最后一次反馈或提示覆盖 |

验收标准：

- 点击"有帮助"后，无需填写内容即可提交到云端。
- 点击"有问题"后，才进入问题类型选择状态。
- 提交成功后，本地 Dexie 记录状态同步更新。

### 6.4 问题类型选择

用户点击"有问题"后，展示问题类型选项。

| 类型 | 说明 |
|------|------|
| 漏了重要条款 | 系统未识别出关键付款、质保、风险或其他条款 |
| 判断不准确 | 抽取内容存在理解偏差或结论不符合合同原文 |
| 风险等级不对 | 风险严重程度过高或过低 |
| 内容看不懂 | 结果描述不清晰、表述难以理解 |
| 其他 | 无法归入以上类型 |

验收标准：

- 用户点击"有问题"后才出现问题类型。
- 用户不选择问题类型也可以继续提交。
- 问题类型保存到反馈记录中。

### 6.5 可选补充说明

| 项目 | 说明 |
|------|------|
| 字段 | comment |
| 必填 | 否 |
| 长度 | 建议 0-500 字 |
| 文案 | "愿意的话，补充一句哪里不对" |

### 6.6 后台自动采集字段

提交反馈时，系统自动记录以下字段：

| 字段 | 说明 |
|------|------|
| analysisTime | 分析完成时间或反馈对应的分析时间 |
| modelName | 本次分析使用的模型名称 |
| promptVersion | 本次分析使用的 prompt 版本 |
| resultSummary | 分析结果摘要 |
| riskItemCount | 风险项数量 |
| contractText | 合同原文 |
| user_id | 用户唯一标识（浏览器 UUID 自动生成） |

合同原文属于敏感数据，数据库表应仅允许服务端写入、按 user_id 过滤读取。

### 6.7 反馈 API 接口

#### 6.7.1 提交反馈 — POST /api/feedback

| 项目 | 说明 |
|------|------|
| 方法 | POST |
| 认证 | 通过 `x-user-id` 请求头传递用户标识 |
| 输入 | 用户反馈动作 + 当前历史分析上下文 |
| 输出 | `{ feedbackId: string; stored: boolean; message: string }` |
| 存储 | PostgreSQL `analysis_feedback` 表 |

#### 6.7.2 反馈列表+统计 — GET /api/feedback

| 项目 | 说明 |
|------|------|
| 方法 | GET |
| 认证 | 通过 `x-user-id` 请求头传递用户标识 |
| 分页 | 支持 `page` 和 `pageSize` 参数 |
| 输出 | `{ list, total, stats }`，其中 stats 包含各分类的 COUNT 统计 |

#### 6.7.3 反馈详情 — GET /api/feedback/[id]

| 项目 | 说明 |
|------|------|
| 方法 | GET |
| 认证 | 通过 `x-user-id` 请求头传递用户标识 |
| 过滤 | 同时校验 `id` 和 `user_id`，跨用户返回 404 |
| 输出 | 单条完整反馈记录（含 contractText） |

### 6.8 我的云端总览（Tab 2）

| 项目 | 说明 |
|------|------|
| 触发位置 | 反馈管理页面的第二个标签页 |
| 数据源 | PostgreSQL 云数据库 |
| 展示内容 | 统计卡片（总数/成功/失败/问题数）、分类分布饼图、筛选栏、分页列表 |
| 操作 | 可展开单条反馈查看完整详情（含合同原文） |

验收标准：

- 切换到"我的云端总览"标签后，加载当前用户的云端反馈数据。
- 显示全局统计概览（单次 SQL 聚合查询）。
- 支持分页浏览历史反馈记录。
- 可展开查看单条反馈完整详情。

## 7. 数据模型

### 7.1 PostgreSQL 表结构（analysis_feedback）

```sql
CREATE TABLE IF NOT EXISTS analysis_feedback (
  id              SERIAL PRIMARY KEY,
  user_id         VARCHAR(64) NOT NULL DEFAULT 'anonymous',
  contract_id     TEXT NOT NULL,
  batch_id        TEXT,
  file_name       TEXT,
  feedback_type   VARCHAR(16) NOT NULL,
  problem_category VARCHAR(32),
  comment         TEXT,
  analysis_time   TIMESTAMPTZ,
  model_name      VARCHAR(128),
  prompt_version  VARCHAR(64),
  result_summary  TEXT,
  risk_item_count INTEGER DEFAULT 0,
  contract_text   TEXT,
  status          VARCHAR(16) NOT NULL DEFAULT 'submitted',
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- 索引
CREATE INDEX idx_feedback_user_id ON analysis_feedback(user_id);
CREATE INDEX idx_feedback_created_at ON analysis_feedback(created_at DESC);
CREATE INDEX idx_feedback_type ON analysis_feedback(feedback_type);
CREATE INDEX idx_feedback_contract_id ON analysis_feedback(contract_id);
CREATE INDEX idx_feedback_problem_cat ON analysis_feedback(problem_category);
```

## 9. 安全与隐私要求

1. 合同原文默认仅用于内部复盘和技术优化。
2. **所有 API 查询必须携带有效的 `x-user-id`，否则返回 503**。
3. **所有查询结果强制按 `user_id` 过滤，杜绝跨用户数据泄露**。
4. 跨用户尝试访问其他用户的数据返回 404（而非暴露数据不存在的信息差异）。
5. 日志中避免打印完整合同原文和 API Key。
6. PostgreSQL 密码等敏感信息通过 `.env.local` 管理，不提交到代码仓库。
7. `NEXT_PUBLIC_` 前缀变量会打包进前端代码，注意不要将敏感变量此前缀暴露。
